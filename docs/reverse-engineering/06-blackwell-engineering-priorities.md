# Blackwell engineering priorities: what source evidence does and does not justify

**Status:** static source review only. Hardware facts such as advertised bandwidth and SM count should be confirmed on the Zephyrus when available. A CUDA `-arch=sm_120` build, passing host math tests, or the existence of a source template does not establish a specific kernel runs efficiently on this laptop.

## Separate four often-confused operations

1. **Offline quantization:** transforms original float weights into an EXL3 trellis, per-weight codebooks and side vectors. The native exllamav3 `quantize_tiles_optimized.cuh` explicitly has **sm_120-specific** kernel sizing and register-pressure commentary; this affects creating a checkpoint, *not* inference time. Its optimized source/dispatch is in [`quantize_tiles_kernel.cuh`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/exllamav3_ext/quant/quantize_tiles_kernel.cuh) and [`quantize.cu`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/exllamav3_ext/quant/quantize.cu). Do not count an offline quantizer speedup as higher model tok/s.
2. **Model-weight decode during inference:** native EXL3 trellis GEMV/GEMM or GGUF quant MMVQ, independent of KV compression. For native EXL3, [`exl3_gemm.cu`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/exllamav3_ext/quant/exl3_gemm.cu) selects small-m GEMV or cooperative quant GEMM and hashes autotuning decisions by compute capability and SM count. Native Python [`exl3.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/modules/quant/exl3.py) chooses direct quantized matmul for <=144 rows by default and f16 reconstruction above; author GGUF source uses direct <=16. Optimize the **executed branch** and actual width, not the marketing quant name.
3. **Attention KV cache layout and consumption:** Jake's [`fattn-mma-turbo.cuh`](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/fattn-mma-turbo.cuh) specializes raw compressed q8/turbo3 K/V input to a templated MMA attention device kernel: `launch_fattn` is called with `need_f16_K=false, need_f16_V=false`, so its own path avoids separate full f16 staging. The template computes dynamic shared memory, optional compressed cp.async staging and layout from D, width, GQA and device capability. The native [`CacheLayer_quant`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/cache/quant.py) supplies raw packed K/scales/V/scales through `get_qkv()` but `get_kv()` allocates full f16 arrays; verify the **actual attention consumer dispatch** and fallbacks before claiming the 6/5 bit-cache configuration is efficient.
4. **Speculative policy and state:** proposal sampling, verifier math, GDN rollback, grammar/penalty history and CUDA graph lifetime. Native ExLlamaV3 Qwen MTP uses shared head/argmax + ID-match; Jake's sampled q/p-q residual is different. Native [`generator.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/generator/generator.py) holds paged K/V and recurrent `rewind`; author merged independent [GDN replay repair #8](https://github.com/JakeATX/llamAmpere/pull/8). Correctness and effective acceptance must be traced separately from CUDA performance.

## Distinct CUDA architectural hazards

- The older SM86 path contains warp-level `mma.sync.m16n8k16` and shared-memory tiled transforms. Compilation on SM120 does not imply tensor-memory-accelerator or newer architecture features are automatically selected. Do not substitute a hypothetical wgmma/TMA port without first checking whether those instructions are available, appropriate and profitable for the selected width, dtype and Blackwell *consumer* GPU.
- The native source's **offline quantization** comment notes sm_120 register-pressure/unrolling differences at K=6–8 and reserves 512-thread geometry despite smaller blocks doing better on some older SMs. This is evidence of non-portable launch heuristics in general, not proof the *inference* GEMV has the same bottleneck. Inspect PTX/SASS, effective register allocation and kernel launch choice before deriving a new inference design.
- Jake's EXL3 cooperative-grid glue fusion lost to separate launches on a ~1008-block 3090 Ti grid. Another design on a laptop with a different number of SMs, power limit and block layout may shift the trade-off; do not enable default blindly. Native gemm autotune already includes SM count and compute capability: its existing tuned path is the reference to inspect first.
- Sources and precision for EXL3 transform vectors matter: `suh`/`svh` and paired H128 operations are part of the mathematical weight, not optional metadata. Some GGUF generic backend fallbacks ignore these extra graph sources and may return incorrect logits. A valid new SM120 kernel must implement the entire operator and fail closed on unsupported shapes/layouts. Compare per-tensor reconstructed weights against a separate reference before end-to-end token tests.

## Implementation-ready *static* design proposals (not benchmark claims)

**PREFILL-1:** For the GGUF route, implement or adapt a compatible trellis-direct GEMM at effective width 17–144 with **bounded workspace** and complete transform semantics. Its native precedent is already in `exl3_gemm.cu`; insist on source attribution and a non-SM120 fallback. For native `T>144`, evaluate on-chip tiled decode against its existing reconstruct+GEMM threshold, separating kernel launch/transforms, input/output dimensions and model-quality parity. Do not create a persistent reconstructed 27B full-f16 weight cache in 16 GiB.

**ATTN-1:** Trace q8/turbo3 target singleton vs verify 2–5 and draft singleton separately using the author's path census and native engine's corresponding fused-attention selection. Only propose a Blackwell attention port after the dtype/width actually dispatches to a slower generic path. Pay attention to GDN's state and independently selected draft cache format.

**MTP-1:** Instrument exact proposal law, effective p/q vs id-match fallback, accepted output/round and target/drafter verified state. Implement CPU-only independent sampling tests and full token-level C++/CUDA parity before adjusting rejection behavior. The `O(|p|×|q|)` list-search complexity in Jake's verifier may be practically small when `q` is top-k20; it is not an established latency hotspot.

**MEM-1:** Derive resident weights **tensor-by-tensor** (trellis, output head, embedding, GDN exceptions and scale vectors), cache allocated pages/bits/scales, recurrent snapshots, per-layer reconstruction scratch, CUDA graphs and Windows/driver reservations. Distinguish `-c` maximum, filled tokens, reserved pool and whole-card resident peak. A 3.0-bpw model+MTP has already approached the 16 GiB whole-card bound in Jake's 65.5K prompt fixture; do not promise 100–120K on this card from the advertised quantization rate.

**Evidence gates:** pinned source diff and shape/dispatch proof → CPU mathematical tests → source-appropriate CUDA parity on real Blackwell → identical workload, quant/model-quality and acceptance-controlled comparison → sustained-power/temperature confirmation. The latter hardware stages are **not** reported as complete.
