# 16 GiB EXL3 and hybrid-memory reverse engineering

**Evidence:** author [EXL3 format specification and actual results](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/docs/exl3.md); [GEMV CUDA](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/exl3-gemv.cu); [decode / prefill dispatch](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/exl3.cu); [KV inventory](https://github.com/JakeATX/llamAmpere/blob/36a6bca81/QWEN_AMPERE.md). Source pin c7a3a742 is **later** than the frozen v0.3 article pin; these files describe experimental v0.3.1 features as of 2026-09-19. No model file was downloaded, no Zephyrus GPU was accessed. Memory arithmetic below is a model, not a VRAM-fit certificate.

## 1. The true EXL3 mathematical operator

A bare EXL3 trellis is **not** the full linear weight. Conceptually, for input x the linear path is `y = diag(svh) · H128 · C_trellis · H128 · diag(suh) · x`, with 128-element block Hadamards, normalization as implemented by the corresponding CUDA glue and f16/f32 arithmetic. `suh[K]` and `svh[N]` are companion per-input/per-output vectors. The GGUF loader represents these as `tensor.suh` and `tensor.svh`; the model graph attaches them as extra sources to the MUL_MAT result and CUDA applies them through glue or fused kernels. Ordinary GGML fallback that computes only the trellis matrix **loses the transforms and gives the wrong model**. This is an architectural constraint, not an optional speed setting.

Per [format docs](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/docs/exl3.md), each 16×16 tile encodes 256 weights in `32 × bits` bytes: at 3 bits, 96 B/tile exactly; at 4 bits, 128 B/tile. Bytes are k-tile major `[K/16][N/16][16*bits]` int16 words. The source implements `mul1` codebook only, not interchangeable older EXL3 codebooks; block Hadamard length 128 must match converter metadata. Nonlinear tensors, embeddings and some non-EXL3 matrices retain conventional types. The reported 3.0-bpw checkpoint has 400 EXL3_3, eight EXL3_4, and a separately protected EXL3_6 `output.weight` plus mixed ordinary tensors; **3 bpw does not mean every tensor occupies 3 bits**.

### Actual CUDA tile decoding, traced

[`k_exl3_gemv`](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/exl3-gemv.cu#L18-L150) uses persistent four-warp blocks traversing `(n-tile, k-split)` work items. Each warp decodes a 16×16 trellis tile from a tail-biting bitstream. For <=4 bpw, 32 warp lanes can collectively fetch a tile with coalesced one-word-per-lane loads, then shuffle to obtain neighboring bit windows; for 5–8 bits, each lane reads three words. The 16-bit windows go through a multiply/byte-dot-product codebook realization (`mul1`) and are packed into four half2 row pairs. Its lane arrangement is chosen to directly match the fp16 `mma.sync.m16n8k16` B operand format for multiple query columns. At width 1, the kernel instead computes half2 FMA. At width 2–16 it uses tensor-core MMA, periodically folds f16 partials into f32 and completes split-K reduction in `glue_out`.

**SM120 design consequence:** the `mma.sync` instruction may compile and execute on Blackwell, but that is NOT evidence it is the best decoder for 3-bpw at width 1–5. The trellis multiply chain, bit unpack and Hadamard glue add instruction cost; narrower weight bandwidth alone does not predict a faster model. Retain a simple warp-level MMV path at T=1, profile register pressure and instruction stalls at T=2–5, and only justify a Blackwell-specific MMA layout if it beats the compatible baseline at those actual shapes. Do not port SM86 launch geometry or cp.async staging on faith.

### The documented prefill cliff is a source-level branch

[`ggml_cuda_mul_mat_exl3`](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/exl3.cu#L178-L245) computes total activation width `T`. If `ggml_cuda_exl3_gemv_supported(T)` it runs trellis-direct (`EXL3_GEMV_MAX_T=16` in the GEMV source). Otherwise, for `T>16` it allocates temporary `K×N` f16 workspace, reconstructs **every** trellis weight into that full matrix, applies the input glue, runs cuBLAS GEMM and then output glue. Every independent linear layer incurs that reconstruction. For large K/N this converts an in-cache 3-bit representation into two-byte weights on the hot prefill path and repeatedly consumes reconstruction bandwidth and workspace. The author reports EXL3 prefill ~2.8× slower than the ATX IQ4_XS path on his tested setup. A *trellis-direct GEMM / tiled on-chip decode* is a concrete separate project, not solved by making width-1 GEMV faster.

The source reports that a cooperative-grid attempt fusing all glue phases lost ~10.6 microseconds/call to grid barriers on a persistent ~1008-block grid; `GGML_CUDA_EXL3_FUSED=1` remains opt-in. First candidates for SM120: keep transform stages independently captured in CUDA graphs; cache/reuse decoded tiles only inside a bounded workspace if safe; use fused GEMM tiles that decode on load directly into tensor-core operands; maintain exact Hadamard/scale transform semantics; compare performance for T=17,32,64,128,512,1024 and memory peaks before proposing persistent full-matrix reconstruction. These are **research designs, not built kernels**.

### Correctness hazards in this particular GGUF integration

The author's docs explicitly note that `src[2]`/`src[3]` carry EXL3 side transforms but `supports_op`, generic backend fallback, graph reuse and allocator were not comprehensively extended for extra sources in that revision. There is no full backend-ops test coverage of the new EXL3 type, only reference converter/kernel parity and limited end-to-end quality runs. Never use this implementation with an unexpected CPU fallback and assume the returned logits are meaningful. A Zephyrus port requires a backend capability check that either performs the complete operator (trellis + both transforms) or rejects the graph. Require converter tests for grouped GDN V permutation, output head, MTP projection, fused QKV and gate/up tensor views; never enable `--fuse-test` (its own docs say it can output a numerically wrong model).

## 2. Derive actual context memory from model shapes

The author's runbook states 16 attention layers, 4 KV heads and 256 head dimensions; 48 other layers use recurrent state. Therefore each target token has `16 × 4 × 256 = 16,384` K elements and the same number of V elements. q8_0 uses 34 B for 32 elements = 17,408 B/token for **target K**. His optimized turbo3 V budget is 6,400 B/token. The **separate drafter** q8_0 K+V adds 2,176 B/token. The quoted total is precisely `17,408 + 6,400 + 2,176 = 25,984 B/token` for a single running sequence, excluding recurrent state and allocator overhead. Choosing q8_0 V increases the target V from 6,400 to 17,408, i.e. total `36,992 B/token`; the measured per-token delta is 11,008 B, not an arbitrary '8-bit KV approximately 2× larger' estimate.

Nominal active-context pool from those fixed bytes: 16,384 tokens = 406 MiB; 32,768 = 812 MiB; 65,536 = 1,624 MiB; 102,400 = 2,538 MiB; 131,072 = 3,248 MiB. These are binary MiB and **are not the whole-card memory use**. They omit model weights, recurrent state, per-layer memory padding, temporary activations and engine/driver/desktop reservations. The `-c` allocation limit, populated active tokens, retained prompt cache, MTP draft-cache length and working set are separate quantities; record them separately.

### Published 24 GB GPU observations that bound plausible 16 GB choices

The author's v0.3.1 [EXL3 study](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/docs/exl3.md) reports the 3.0-bpw mixed model file at 10.91 GiB, whole-card peak 14,403 MiB in a ~20K-prompt MTP-4 run, and peak 15,688 MiB with a **65,531-token prompt** and subsequent decode. The headline prompt depth is not the whole allocated `-c` nor necessarily the maximum active KV after generated tokens. For 3.5 bpw the ~20K fixture already peaked at 15,756 MiB, leaving ~628 MiB under 16,384 MiB **before differences in desktop overhead**. The 4.0-bpw MTP fixture peaked at 17,154 MiB and is therefore incompatible with a 16 GiB whole-card cap in that configuration. The same 3.0-bpw study found 80.67 tok/s (short fixture) and 74.89 tok/s on its 65.5K-prompt case on RTX 3090 Ti: neither speed is a laptop forecast.

**Capacity implication:** choose a 3.0-bpw mixed-precision reference rather than a blind 3.5–4.0-bpw default. Preserve the output head at higher precision and GDN-sensitive tensors at suitable precision. Do not claim 100–120K context fits on Windows with this particular q8_0/turbo3 cache; use an actual whole-card allocation/fragmentation report. An alternative KV compression format can move that limit if (and only if) the selected engine has a fast fused attention path and GDN state remains correct.

## 3. Quality-aware allocation before higher context or lower bpw

A smaller *average* bits-per-weight can be worse in practice if it damages the output projection, GDN gate/alpha/beta, attention K/V, MTP projection or token embedding. Retain an explicit per-tensor quantization manifest including physical allocated bytes, dtype, quantization algorithm and validated original source tensors. EXL3 format's side vectors and inverse Hadamards must always accompany a repacked/merged tensor. Preserve shared `suh` for fused QKV and gate/up and verify equality rather than assuming it. Measure quality separately at short and long context, with and without MTP and with kv compression. Do not use token/s alone to select 2.0 bpw over a 3.0-bpw quality reference.

## 4. Independent optimization lanes rather than a premature monolithic fork

**Lane A**: a stock runtime with working SM120 and a mixed 3-bpw quant; record true supported KV format and exact draft model memory. **Lane B**: Jake's GGUF-native EXL3 port, with hard rejection of incomplete backend fallback and direct shape-based kernel dispatch verification. **Lane C**: ExLlamaV3's native EXL3 representation, MTP and optimized quantized KV; inspect that project's exact version for Blackwell support rather than assuming one particular community fork has identical semantics. Compare all three on equivalent quality and active context. Only after profiling implement one isolated optimization: either direct EXL3 prefill GEMM, warp/tile decoder for T=1–5, or the actual compressed attention bottleneck. Keep a known-correct host and CUDA fallback for each experimental lane.
