# Native ExLlamaV3 allocation lifecycle: pinned source and 16 GiB design

**Source pin:** `turboderp-org/exllamav3@02aef45cd681b960a00afcd0749a4ab99e6c1bfe`; checkpoint: `turboderp/Qwen3.8-27B-exl3@004a887127d8304ca2d5475d3a3c41f1761fdd27`, `SC_3.00bpw_H4_V4`. This is a **static source trace only**. No model loading, GPU forward, compilation, inference or benchmarking on Zephyrus. The existing on-disk tensor manifest is accurate; previous all-weights-on-GPU budget was not a native-loader residency trace.

## 1. Where weight bytes reside

[`architecture/qwen3_5.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/architecture/qwen3_5.py) creates an `Embedding` module for `model.language_model.embed_tokens`. [`modules/embedding.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/modules/embedding.py) sets `caps['prefer_cpu']=True`; both `_load_single()` and `_load_autosplit()` honor it and call its loader on **CPU**, preserving the BF16 source dtype (`allow_bf16=True`). Its ordinary forward gathers small embedding outputs on the CPU and sends them to the next layer, with optional **CPU pinned staging per activation shape**. It does not first place the 2,542,796,800-byte embedding on GPU. This is a **2,425 MiB difference** between serialized text bytes and native GPU-weight inputs, not additional free VRAM observed on the machine. Host RAM and CPU/PCIe embedding latency remain relevant in the eventual end-to-end test.

`model_init.py` instantiates the MTP as a separate component and loads the draft component **before** the target. The MTP constructor declares one self-attention layer and own `mtp.*` projections; `generator/generator.py` later invokes its `attach_to(target)`. [`architecture/qwen3_5_mtp.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/architecture/qwen3_5_mtp.py) holds weak references to the target embedding and **target lm_head**. These weights are not separately serialized under MTP and should not be counted again. The target lm_head remains a 4-bpw EXL3 GPU-weight input (~606.73 MiB payload), whereas the CPU embedding remains a BF16 host-weight input. A text-only model factory does not instantiate the optional vision component; `vision_pinned` is a separate opt-in transfer mechanism and **does not mean the text embedding lives on GPU**.

## 2. What the loader does rather than what a model file suggests

[`model/model.py::load_gen`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/model/model.py) chooses `_load_single()` for an explicit device, or `_load_autosplit()` by default. `reserve_per_device=0.5` GiB is a default **PyTorch budget**, not a hard reservation against the GPU's actual other-process/display usage. `_load_autosplit()` in [`model/model_ls.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/model/model_ls.py) executes a **synthetic forward after each module is loaded**, including cache-aware attention/recurrent paths. It measures peak allocations and keeps both a max-transient budget and a physical-headroom margin (default 256 MiB). Do **not** call autosplit, `model.load()` or `autosplit_no_forward` to gather “harmless inventory” during the no-model-execution phase: even with dummy-forward disabled, the code would allocate model weights and caches on GPU. The present static planner executes neither.

The source loader brackets eligible modules with `begin_deferred_load`/`end_deferred_load`. [`loader/safetensors.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/loader/safetensors.py) normally writes directly into persistent GPU destination tensors; **transpose, padding or fp32 conversion** may first allocate a separate temporary tensor. Small deferred tensors can share 128 MiB slabs (maximum individual tensor 16 MiB, up to eight open blocks per device), creating bounded-looking but not uniquely predictable slab tails. `g_tensor_cache.drop_all()` at the end of loading clears the shared dictionary, **not tensors still referenced by modules or graph objects**. The runtime allocator may also retain freed blocks. None of these sources proves a fixed delta from on-disk payload to VRAM-resident weight bytes.

## 3. Decode, prefill, and conditional expansion

[`modules/quant/exl3.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/modules/quant/exl3.py) uses a direct trellis kernel for activation width <=144 by default. Beyond it, the **current single layer** allocates an FP16 reconstructed weight matrix; `out_features >32768` caps each reconstructed **slice** at 32768 columns, and the process reuses a slice buffer. The largest individual slice in the pinned text+MTP checkpoint is the 5120x32768 output-head slice: **320 MiB**. This is not a permanent 27B fp16 model, nor an upper bound for all simultaneous activations. **Ordinary generator output-head work normally stays below the 144-row reconstruction threshold** (`model/model_ls.py` trims last tokens before the logits layer, default load measurement uses at most 32 output rows, and MTP samples a short head step). Thus the largest *non-output-head* reconstructed matrix in the pinned text+MTP inventory is **170 MiB**, a more relevant possible prefill transient. The 320 MiB head path remains possible for wider custom logits calls but is not an asserted default prefill expense. That code also separately allocates transformed activation (`xh`) and output (`y`) buffers, potentially concurrent with the reconstruction. The optimizer must budget their shapes and keep them independent of the serialized EXL3 allocation.

[`cache/quant.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/cache/quant.py) allocates persistent packed K/V and per-32-element scales up front. Its `get_qkv()` returns packed tensors; its **fallback** `get_kv()` allocates an FP16 K and an FP16 V tensor spanning the **entire reserved per-layer cache pool**, regardless of how much of the pool has actual tokens. For 4 KV heads x head dim 256, one layer's full-cache fallback costs 4096 bytes per reserved token: 256 MiB at 64K, 512 MiB at 128K. This is a transient *per-layer*, not 16 layers of permanent FP16 KV, unless something else retains those buffers.

[`modules/attention_fn/dispatch.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/modules/attention_fn/dispatch.py) enters the packed-cache path only for `_qc_staging<2`, `CacheLayer_quant`, `compand_a==0`, Q in FP16, head dim <=512 divisible by 32, and `cu_seqlens is None`. Otherwise the full-cache `get_kv()` path may be taken. Native Qwen's configured attention head dimension 256 passes the static dimensional predicate; **query dtype and runtime arguments still have to match**, and no actual runtime dispatch was executed here. The quant-direct dispatcher explicitly refuses unsupported kernels rather than allowing a cache-less backend to ignore its packed cache.

[`modules/attention_fn/triton_paged.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/modules/attention_fn/triton_paged.py) uses online packed-cache decode. The default `_qc_staging=1` may stage a sufficiently large **causal prefill** query (`q_len>=256`, eligible no-new-KV path) into an FP16 K/V buffer sized to the *referenced* cache window, optionally bounded by `max_kv_len`; allocated pages are rounded up to a power of two. `_qc_staging=0` disables that staging; `_qc_staging=2` intentionally selects full-cache FP16 expansion and is **not included** in the proposed low-VRAM profile. For bsz=1, a hypothetical full-window upper sizing at 64K/128K is 256/512 MiB per attention call; actual active window may be smaller. An allocation can disappear as a Python tensor and **still contribute to the caching allocator's reserved high-water mark**.

## 4. Actionable architecture constraints

The [CPU-only native loader ledger](../../tools/native_loader_ledger.py) uses the audited 3,080-tensor inventory to separate **on-disk bytes / CPU embedding / candidate GPU-weight input / persistent KV+recurrent / one reconstructed matrix / one staged attention window / full-pool fallback**. Its components are deliberately **not summed as a peak-memory certificate**: unknown activation overlap, graph lifetime, per-module pinned slabs, CUDA context, host-to-device staging, allocator fragmentation, separate decode scratch and Windows graphics remain unquantified. It cannot detect kernel-dispatch regressions; the original quant-direct eligibility checks must stay intact.

Do not choose a context default solely from the previous all-weights-on-GPU estimate. Keep `vision=False`, `slots=1`, explicit MTP history, and a user-selected KV and context budget as separate parameters. For a low-VRAM first implementation, use online compressed KV as a **design candidate**, not a proven optimum: disabling staging may reduce peak memory but worsen prefill speed, and the model still needs correct recurrent rollback and usable code-generation quality. A fail-closed preload should reject missing metadata, mismatched tensor shapes, unsupported quant operators and negative *modeled* headroom without silently offloading to an unintended path. Later, the final authorized GPU stage must record real free/reserved/allocated/peak bytes at start, after MTP load, after target load, after graph capture, after long prefill and during sustained decode, plus actual attention and GEMM dispatch.
