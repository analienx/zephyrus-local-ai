# EXL3 prefill: compare native direct GEMM and GGUF reconstruction, at source level

**Pinned native source:** [`turboderp-org/exllamav3` 02aef45cd681b960a00afcd0749a4ab99e6c1bfe](https://github.com/turboderp-org/exllamav3/tree/02aef45cd681b960a00afcd0749a4ab99e6c1bfe). **Pinned author source:** [`JakeATX/llamAmpere` c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee](https://github.com/JakeATX/llamAmpere/tree/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee). The latter is newer than the v0.3 benchmark revision. These are static code observations; no local model/SM120 execution or cross-engine speed claim.

## 1. Native ExLlamaV3's direct GEMM already exists: don't reinvent it as though nobody built one

[`exllamav3/modules/quant/exl3.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/modules/quant/exl3.py#L1-L215) sets `AUTO_RECONSTRUCT_THRESHOLD=144`. `LinearEXL3.forward` counts activation rows as `rows=x.numel()//x.shape[-1]`: when `rows <= 144`, or `config.infer_params.no_reconstruct` is set, it uses the `BC_LinearEXL3.run_alloc` quantized linear path directly. With larger rows by default it calls `reconstruct_hgemm`. The latter reconstructs fp16 matrices, with output-dimension slices capped at 32768 columns, and uses `ext.hgemm_recon`. It has an additional *fused transform-into-reconstruction* path at `rows>=1024` (when K/N multiples of 128) that eliminates standalone Hadamard glue launches; this is a distinct optimization from eliminating full weight reconstruction. Both paths still allocate transient f16 weights. These thresholds were not inferred from benchmarks; they are explicitly present in the native Python source.

[`exllamav3/exllamav3_ext/quant/exl3_gemm.cu`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/exllamav3_ext/quant/exl3_gemm.cu#L1-L335) implements a native trellis GEMM kernel dispatcher. It handles quantized B plus `suh`, transformed-input scratch and `svh` as explicit kernel args, chooses a small-m GEMV route opportunistically, else autotunes cooperative GEMM launch shapes against `(m,k,n,bits,codebook,compute capability,SM count,output dtype)`. Its autotune hash caps m to a set of approximate size classes; capture uses explicit graph parameter registration for A, quant trellis, output and transform pointers. An experimental `EXL3_INT8_GEMV=1` is guarded by mul1, is only attractive for narrow m, and is **not graph-capturable**; graphed callers fall through. The native implementation therefore offers an existing source-grounded approach to trellis-direct modest-width matmuls and avoids a mandatory full-f16 reconstruction for 17<=T<=144 unless a different branch overrides it.

[`JakeATX/llamAmpere ggml/src/ggml-cuda/exl3.cu`](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/exl3.cu#L178-L255) dispatches trellis-direct through `ggml_cuda_exl3_gemv_supported(T)`, where the corresponding [`exl3-gemv.cu`](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/exl3-gemv.cu#L1-L125) defines a width up to 16. For T>16 it reconstructs `K*N` fp16 weights then invokes cuBLAS. **This is a source-level explanation of why native ExLlamaV3 and the GGUF-native port may behave very differently at 17–144 activation rows, even though they both advertise EXL3.** It is a difference in dispatch and implemented quantized GEMM, not an established speed ratio.

## 2. What to implement for the Zephyrus, conditionally

- First retain the proven existing native direct-quantized path and its transform/graph semantics for narrow prefill. Do not write a new Blackwell GEMM before examining native `exl3_gemm_kernel.cuh` tile layouts and actual device architectural guards. The code's autotune dimensions include cc and number of SMs, so porting a stored launch-shape policy from SM86 to SM120 would be unsound.
- For a GGUF-based product, a **bounded direct EXL3 GEMM for 17–144** is the most concrete missing kernel class compared with the native runtime. Porting or reimplementing requires matching codebook, `suh/svh`, H128 transforms, exact fused tensor views, graph allocator and backend capability checks. License/attribution must be preserved for reused native code; do not copy source naively into an incompatible GGML layout.
- For >144 rows, both audited implementations use full-f16 reconstruction by default (though the native path chunks very wide output heads and optionally folds Hadamards into reconstruction at >=1024). Investigate tile-on-load trellis decode vs reconstructed GEMM for this width class separately; potential bandwidth wins compete with decode instruction overhead, occupancy and tensor-core throughput. Do not claim one kernel can dominate every prefill width.
- A prefill-only full-weight cache trades 16 GiB VRAM capacity against latency; permanently caching an entire 27B fp16 model is infeasible on this device. Ephemeral per-layer reconstructed weights, bounded scratch and tiled approaches must be evaluated with whole-card memory accounting. Cache only a demonstrably hot submatrix within an explicit GPU budget.
- Chunked prefill interacts with MTP/KV/recurrent-state correctness: batch chunk dimension may change kernel choice and recurrent snapshot lifetimes. Compare the same active token counts, sequence length and exact prompt content; avoid treating `T=144` kernel threshold as an intrinsic quality boundary.

## 3. Outstanding audit gates

Inspect `exl3_gemm_kernel.cuh`, EXL3 native graph capture boundaries and the ggml loader's nonstandard `src[2]/[3]` transform semantics. Verify whether Qwen3.8's actual EXL3 checkpoint matches this native architecture and how many activation rows each *real* coding-agent prefill stage issues. Verify supported SM120 kernels and numerical parity before touching CUDA. Published 3090 Ti throughput and any third-party laptop results remain **external measurements**, not acceptance criteria or a promised Zephyrus improvement.
