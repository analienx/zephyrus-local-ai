# Native ExLlamaV3 vs llamAmpere: source-level engine differences

**Audited native revision:** [`turboderp-org/exllamav3` 02aef45cd681b960a00afcd0749a4ab99e6c1bfe](https://github.com/turboderp-org/exllamav3/tree/02aef45cd681b960a00afcd0749a4ab99e6c1bfe), author main revision inspected separately [`JakeATX/llamAmpere` c7a3a742](https://github.com/JakeATX/llamAmpere/tree/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee). This compares *source at a particular revision*, not a hardware performance test. Qwen3.8 must be verified against the actual architecture registration/model assets, not assumed equivalent to every Qwen3.5/3.6 variant merely because source shares a family name.

## 1. The native Qwen MTP head reuses the target head, but does not implement Jake's p/q policy

[`qwen3_5_mtp.py` constructor and attach_to](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/architecture/qwen3_5_mtp.py#L20-L260) creates MTP-specific input/projection, one or more MTP TransformerBlock(s), and a final norm. In `attach_to` it takes weak references to target Embedding and target `lm_head`, explicitly exports the target's post-final-RMSNorm hidden state (the code says not pre-norm as in DeepSeek/GLM). Its `sample_from_state` invokes the borrowed target `lm_head` and chooses `torch.argmax(logits)`; the tensor-parallel alternative also returns `argmax`. Default draft size is 4 in this class. Therefore do **not** budget a second full resident lm_head for this native *attached* path without checking whether a particular loader duplicates weights; and do not assume it draws draft tokens from temperature-adjusted q or records proposal distributions for exact p/q.

[`generator/generator.py` speculative consumer](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/generator/generator.py#L1130-L1260) samples the target at every verified row, accepts the proposed draft only while sampled target ID matches the proposed ID, and otherwise truncates the remainder. It also interrupts acceptance on recurrent checkpoint boundaries and handles EOS, filter/banned-string rewinds and request requeue. No q distributions or target-minus-q residual sampler are visible in this audited path. A proposed p/q port would change semantics, create proposal distribution storage/sampling costs and need new mixed constrained/greedy exactness gates. Published native ExLlamaV3 MTP throughput at temperature >0 and Jake's p/q throughput are **not directly comparable as kernel speed**.

## 2. Quantized-KV representation: exact allocated bytes, not nominal bpw

[`CacheLayer_quant` in quant.py](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/cache/quant.py#L10-L154) stores each K/V group of 32 values as `k_bits` or `v_bits` 32-bit words in an int32 tensor plus one fp16 scale for K **and** V. Shape per token per attention layer is `H * D / 32 * b_K` int32 entries for K, similarly V; scales are `H*D/32` fp16 entries each. For Qwen's documented `H=4`, `D=256`, there are 1024 values per K and V per layer. Thus bytes/token/layer = `1024*(bK+bV)/8 + 2*1024/32*2 = 128*(bK+bV)+128`. At native **6/5 bits**, this is 1,536 B per attention layer per token; 16 target attention layers cost 24,576 B/token, and a one-attention-layer drafter with the same cache costs 1,536 B/token, **26,112 B/token total** if one separately populated draft layer and no sharing. This is effectively the same magnitude as Jake's **25,984 B/token** for q8_0-K/turbo3-V plus q8_0/q8_0 one-layer draft. For 100K tokens the native 6/5 16+1 cache is ~2.49 GiB before page padding, allocator, other inference buffers, recurrent states and desktop. This is a source-derived shape calculation, not an observed maximum context.

`max_num_tokens` is rounded/padded to PAGE_SIZE in the native class; the cache is paged, pre-allocated up to configured tokens rather than guaranteed to consume only filled-context memory. `get_qkv` returns raw compressed K/scales/V/scales for an online-dequant attention kernel with no temporary allocation; `get_kv` explicitly allocates/dequantizes fp16 K and V (a potentially catastrophic fallback at long context). Inspect the **executed attention backend dispatch**: whether it calls `get_qkv` or `get_kv`, direct fused 6/5 compressed attention versus dequant fallback, dimensions/alignment constraints and caching of inactive pages. Neither nominal 6/5 nor selected quant cache class proves that compressed attention is active. Separate any additional MTP-cache quant from target cache: the loader may select different draft bits and padding.

For the author's GGUF branch, 16 target attention layers and drafter have source-reported `25,984 B/token` at q8 K/turbo3 V/q8 draft, so a change to native 6/5 **does not automatically free context memory**. Higher-resolution model weights and desktop headroom may be more important than a 128 B/token difference. A genuine lower-memory win requires a measured different KV format/head layout, lower draft overhead or reduced reserved context, with an attention path whose slower dequantization does not erase decode throughput gains.

## 3. Native recurrent rollback is not Jake's repaired state blob

[`generator/generator.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/generator/generator.py#L1040-L1240) passes `recurrent_history=True` on drafted verification, calls `rewind(num_rejected)` on the job's recurrent state after a rejected suffix, and decrements retained page `kv_position` per sequence. It calls `rewind(0)` when all drafted tokens were accepted, and has separate state/loop behavior for EOS, requeue, banned-string checkpoint rewinds and recurrent checkpoint boundaries. This is **not** structurally the same as llama.cpp's recurrent memory snapshot/ingredient-ring implementation from [Jake's September 18 PR #8](https://github.com/JakeATX/llamAmpere/pull/8). Validating one does not validate the other. When introducing speculative-mode or prompt-caching changes, test each engine's own transactional rollback rather than swapping data structures between runtimes.

[`cache/recurrent.py`](https://github.com/turboderp-org/exllamav3/blob/02aef45cd681b960a00afcd0749a4ab99e6c1bfe/exllamav3/cache/recurrent.py#L1-L140) stores checkpoint state in a host-RAM-budgeted LRU. It favors evicting **stranded** checkpoints whose anchor KV page chain has already been evicted: these are not restorable even if checkpoint bytes survive. Checkpoint count, host RAM and KV page residency are distinct from GPU context allocation and must be included in long-lived coding-agent usability tests.

## 4. Source-comparison matrix before profiling

| Property | Jake's GGUF-native EXL3 | Native ExLlamaV3 (pinned revision) | Consequence |
|---|---|---|---|
| Weight GEMV | GGUF trellis decode width 1–16 with `mul1`, Hadamard/side-tensor glue | Native EXL3 kernel/loader family; audit exact per-width dispatch separately | Same file-format name does not imply identical decode throughput or tensor layout assumptions. |
| Prefill | **T>16 reconstructs a full f16 weight and cuBLAS GEMM** | Must inspect native prefill quant kernel and fallback; not yet established in this audit | Do not assume matching TTFT or VRAM workspace. |
| Qwen MTP proposal | Per-request mirrored q distribution when supported, with identity fallback | Borrow target head + `argmax` | Distinct proposal and acceptance laws. |
| Verification | Coupled exact p/q + residual or identity fallback | Sample target, ID-match, reject suffix | Compare effective acceptance and per-round cost separately. |
| KV cache | q8_0 K/turbo3 V + q8_0 one-layer draft: 25,984 B/token | 6/5 K/V quant + one same-format draft layer: modeled 26,112 B/token | Both around 2.5 GiB/100K; page and reserved-size effects still count. |
| Recurrent state | llama.cpp snapshot/replay and 2026-09-18 repair | per-job recurrent history/rewind and host-LRU checkpoint cache | Different rollback correctness/eviction contracts. |

## 5. Source-grounded priorities, not a premature benchmark plan

**Immediate static tasks:** inspect native EXL3 CUDA quant/linear prefill dispatch and format metadata; verify Qwen3.8 family registration and model/quant conversion compatibility; establish exact 6/5 fused attention path and expected fallback behavior; inspect native draft-cache precision and residency. Compare target-vs-draft head sharing to GGUF's indexed-map fast path without attributing model-weight memory savings to a shortlist that merely accesses fewer rows. The C++ p/q nested q lookups have a worst-case `O(|p|*|q|)` shape, but under Jake's documented temperature-1/top-k20 sampler `q` is a small candidate list; do **not** call this a dominant bottleneck without effective candidate counts and host time. Focus source audit first on the repeated full-weight prefill reconstruction and the verified attention/quant format dispatch.

**Boundary:** This is substantive code-path analysis but not a comprehensive line-by-line fork diff, native CUDA parity proof or measured GPU profile. Record remaining unknowns as unknowns; never label a hypothetical SM120 optimization as an implemented speedup.
