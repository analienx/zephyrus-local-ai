# Reference decode path: source-derived mechanism analysis

**Research snapshot:** 2026-09-19. `llamAmpere` published v0.3 measurements target [`36a6bca81`](https://github.com/JakeATX/llamAmpere/tree/36a6bca81); the source inspected here is later [`c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee`](https://github.com/JakeATX/llamAmpere/tree/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee), which includes v0.3.1 EXL3 and 2026-09-18 GDN fixes. **Do not attribute new features or numbers to the older v0.3 release.** The X article URL did not expose its text through the retrieval interface; the author's own article, runbook and source are the accessible primary references. This is a static source audit, not a Zephyrus execution or completed upstream diff.

## 1. Actual computation graph, not a list of flags

In the sequential MTP route, a target forward returns its sampled token and next-token hidden representation; the separate MTP draft context uses the accepted prefix plus that representation, selects a draft head/layer and proposes up to `n_max` tokens. The target verifies the candidate sequence in a *single wider forward*, samples/accepts the longest valid prefix, and on rejection replaces the token from the correct target residual. Both the attention KV and the recurrent state must then agree with **only** the committed prefix before the next round. Server-side prompt prefix reuse must restore recurrent checkpoints as well as the KV cache. See [draft producer](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/common/speculative.cpp), [server orchestration](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/tools/server/server-context.cpp), [MTP model graph](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/src/models/qwen35.cpp).

The per-round wall time is not identical to target model latency: `T_round = T_draft_n + T_verify_width(n+1) + T_sampling_and_rollback + T_gap`. Throughput is `accepted_or_fallback_output_tokens / T_round`. Changing `n` changes both accepted output and wider-verifier work; reporting only acceptance fraction loses the causal decomposition. If a source run records generated tokens `predicted_n` and accepted draft tokens `draft_n_accepted`, its reported verify pass count is `predicted_n - draft_n_accepted` *under that server's accounting*. Verify this invariant against the actual server event log for each engine; do not silently transfer it to different counters in ExLlamaV3.

### Concrete published critical path (v0.2, 100K coding fixture, width 4 on SM86)

The author's [v0.2 article](https://github.com/JakeATX/llamAmpere/blob/44233f009/docs/llamampere-v0.2/ARTICLE.md) measured approximately 21.8 ms body MMVQ, 9.5 ms grouped attention, 6.0 ms singleton attention, 5.9 ms copies/norm/quant/GDN, 3.7 ms drafter head and 1.4 ms target head per verification pass, with 6.3 ms GPU idle outside kernels. **These times are from a different quant, GPU, context and software revision.** They are a decomposition template, NOT Zephyrus predicted times. The head-shortlist feature targeted 3.7 ms; after it and runtime fixes, the author found the next attention/quant bottlenecks changed. Reprofile when changing quant from IQ4_XS to EXL3.

## 2. Why p/q verification is fundamentally different from identity matching

For each sampled draft token `d ~ q`, where `q` must be the **actual** normalized proposal distribution used to sample `d`, the target has distribution `p`. Accept `d` with probability `min(1,p[d]/q[d])` when `q[d]>0`; on rejection sample from `r[i] = max(0,p[i]-q[i]) / sum_j max(0,p[j]-q[j])`. Zero `q[d]` is impossible for a token genuinely sampled from q; treat it as an invalid-state error, not as a reason to divide by zero. If `p=q`, every draw accepts. With a restricted draft vocabulary, q is zero outside the shortlist and the residual still includes those target-only tokens. The resulting next-token law is exactly p **if** the draft draw, recorded q, verifier p, and residual are mutually consistent. [Author v0.3 derivation and tests](https://github.com/JakeATX/llamAmpere/blob/36a6bca81/docs/llamampere-v0.3/ARTICLE.md); [draft source](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/common/speculative.cpp).

Important failure modes from the implementation: the producer only takes exact p/q when request sampling parameters, per-position `result_q` storage and supported sampler conditions exist; if backend sampling already returns a token without its matching distribution the producer switches that position to identity/argmax behavior. It records a full candidate distribution per draft position when exact verification is possible; the q sampler is not reseeded each round. A confidence-based early stop acts *before* verification and cannot be repaired by the residual sampler for a proposal never made. Our telemetry must count actual `pq`, fallback and no-draft positions and emit a reason, never infer mode from the environment variable alone.

**Audit boundary:** the preceding paragraphs inspect the draft producer and the published p/q design. A line-by-line audit of the **target** verifier in `common/sampling.cpp` and `tools/server/server-context.cpp` remains required before porting: grammar, token biases, repetition penalties, top-k/p/min-p ordering, q-zero, token EOS, floating-point normalization, and restoring the accepted-only state. `p` must represent the post-processor target distribution for that exact position; a mismatch between request samplers violates exactness even if a short simulation passes.

## 3. The draft shortlist: cheap projection, NOT free model-weight VRAM

The [shortlist design](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/docs/mtp-vocabulary-shortlist.md) uploads a persistent 65,536-ID int32 map (256 KiB), then views the existing quantized output head as one-row experts through `mul_mat_id`. The target head and target final sampler still cover 248,320 tokens; the draft sampler remaps shortlist-column indices to real token IDs. The map is model-tokenizer-specific. Fast path is conditional: supported CUDA quant dtype, head on expected CUDA buffer, no incompatible LoRA/output-row scaling, and backend sampling for the draft output rows. Unsupported cases silently take full-head projection; record path selection and effective vocab size during tests.

Published projection time on the author's card: full ~1,566 us, 64K shortlist ~388 us, 32K ~196.5 us. Full head weights still reside on GPU: **do not subtract 75% of head VRAM** from fit estimates. The author benchmarked a packed contiguous shortlist *slower* than indexed reads (203 vs 192 us for 32K), and an adaptive hot tail hurt representative throughput ~2.7% despite higher prompt-token coverage. The 64K map was curated with structural-token and non-Latin reserves; a new quant/model/tokenizer requires a new coverage/acceptance audit. A 64K map created for the ATX head must not be reused unvalidated with a differently quantized MTP head: proposals and their probabilities change.

## 4. Compressed attention: prove the executed kernel

[Fused attention dispatch](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/ggml/src/ggml-cuda/fattn.cu) has competing vector, generic MMA and q8_0-K/turbo3-V / q8_0-V fast paths. Dispatch keys include CUDA compute capability, query width, Q head dimension, KV dtype, GQA grouping, mask/bias alignment, and flash-attention compilation flags. `GGML_FATTN_PATH_STATS=1` has a built-in census of path, K/V dtype, D, `n_q`, GQA, packed columns and KV-depth bucket; verify that the **target verify**, **target singleton**, and **draft singleton** use the intended path independently. An environment flag or successful sm_120 build does not establish that a particular specialization actually executes.

The v0.3 article reports the P5c change removing staging/dequant between stored compressed K/V and the attention tile, with its kernel dropping ~456 to ~344 us in its measured case; P6 adds a q8_0/q8_0 drafter fused instantiation, ~321 vs 441 us for an f16 cache and 170-260 MiB of memory regained. A verify-width 6–8 specialization exists but is **off by default** because depth-3 and depth-4 MTP do not reach that width. q5_1 V was ~23% slower on the author's setup because it dispatched to generic attention, even though its memory use lay between q8_0 and turbo3. Our design must choose **format × decode width × backend kernel**, not the lowest nominal KV bits in isolation.

## 5. Kernel-launch and graph overhead: measured bound, not universal advice

The [v0.3 article](https://github.com/JakeATX/llamAmpere/blob/36a6bca81/docs/llamampere-v0.3/ARTICLE.md) records an SM86 production round at 44.8 ms, 88.2% GPU busy, with 5.30 ms idle split among ~1.94 ms kernel launches, 1.71 ms host work, 0.56 ms sync wait and smaller classes. It recorded roughly 378 non-graph kernel launches per round; the large main and draft CUDA graphs were already captured and reused. Thus a generic 'enable CUDA graphs' patch would NOT address that source profile. On the Zephyrus, inventory launch counts, graph reuse, CPU→GPU sync and SM occupancy *at the lower-bit quant's actual verify widths* before attempting new graph or host orchestration.

## 6. High-value negative results to avoid reimplementing blindly

[Author v0.2/v0.3 experiments](https://github.com/JakeATX/llamAmpere/blob/c7a3a742f55d76e46a7c4ccfc40bf01a8be318ee/QWEN38_SM86_FRONTIER_HANDOVER.md): an adaptive draft hot tail decreased throughput; temperature-1 depth 4 lost against depth 3 on representative v0.2 traffic despite winning greedy fixtures; DFlash2 stayed behind sequential MTP on SM86 even after fixing its wider attention path; a persistent cooperative EXL3 kernel with grid barriers lost to separate glue kernels. These are **counterexamples to universal optimizations**, not proof of Blackwell outcomes. For every proposed port, require source rationale, a correctness/parity gate, effective-dispatch tracing, and an A/B with the code path explicitly toggled.
