## Questions that define the port

1. Which changes reduce required bytes/round, which reduce instructions/round, and which reduce rounds/output token? Optimize the actual dominant dimension on *mobile* sm_120, not on sm_86.
2. How much **actual** free GPU memory remains after Windows display/compositor, weights (including the MTP head), recurrent state, target KV, **separate draft KV**, CUDA graphs, allocator/workspaces, and safety headroom? Test reserved and populated contexts separately.
3. Which upstream pathways are exact (same logits/distribution), which change numerical precision or compression, and which intentionally reduce model quality via weight quantization? Treat these as different product claims.
4. Is our bottleneck memory traffic, low-bit dequant, attention over KV, Gated DeltaNet prefill, speculation verification, graph/host overhead, or sustained mobile clocks? Record profiler evidence before editing kernels.

Treat this as an unverified starting hypothesis. Their SM86-specific MMVQ path is separately gated; audit capability dispatch and **do not** assume a build passing implies the optimized route ran.

## Source files to audit at pinned SHA before writing our kernels

- llama.cpp / llamAmpere: `common/speculative.cpp`, `ggml/src/ggml-cuda/fattn.cu`, `ggml/src/ggml-cuda/gated_delta_net.cu`, `src/models/delta-net-base.cpp`, `src/llama-memory-recurrent.cpp`, `src/models/qwen35.cpp`.
- `ggml/src/ggml-cuda/` quantization and MMVQ/MMQ selection: identify exact implementation files with `git diff --name-status` between pinned upstream/TurboQuant/v0.2/v0.3 commits, then map each touched kernel to its dispatch guard, register/shared-memory footprint and minimum CUDA version.
- ExLlamaV3/TabbyAPI: find the *actual* Qwen3.8 loader, MTP verification, EXL3 packed weight/dequant kernels, cache modes, graph capture and SM120 build paths at pinned revisions. Do not assume that llama.cpp flags work in this separate engine.
- Other engines/quantizations: inspect native MTP, 2-bit kernels, FP8/NVFP4 hardware path and public evaluation methodology **before** promising quality/speed.

## Port order and go/no-go gates

**P0 Source reproducibility:** pin commit, model hashes, toolchain, license; extract changed functions + dispatch conditions; check CUDA architectural assumptions and record any pre-existing bugs. **P1 Baseline:** no-MTP vs native-MTP; compare usable 3.0/3.5-bpw EXL3 and low-bit GGUF. **P2 Memory:** quantify target/draft cache and graph/workspace allocation. **P3 Kernel profiling:** separate prefill, singleton decode, MTP draft, target verification, attention, MMVQ, sampler/host. **P4 First optimization:** one narrow, feature-flagged change with exact replay/correctness tests and paired A/B; revert on failure. **P5 Portfolio:** retest cumulative performance, quality and sustained thermals at 16/32/64/100K active context. Never add isolated speedups arithmetically or publish desktop throughput as a laptop result.

### What we still do not know

Actual laptop SKU, CPU, RAM, operating-system backend and WSL driver behavior, current free VRAM, sustained clocks/power, kernel-level profile, model quant quality, MTP support of pinned engine builds and the exact text of the X article. The research ledger is an architecture/source map, **not** evidence of a successful SM120 port or verified model selection.
